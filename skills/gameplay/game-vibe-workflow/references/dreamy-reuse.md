# Dreamy integration before custom infrastructure

Apply in Dreamy/template consumers and when the owner asks for maintainable, production-oriented reuse. The game's visual/behavior contract remains authoritative; integrating a sample does not authorize shipping its unrelated appearance or economy. Preserve existing work and all build/SDK constraints.

## Inspect and decide before coding

Read the root/Bootstrap README, relevant package README, imported `_Feature` README and nearby installer/view/presenter/prefab source. Verify manifest/lock/asmdefs and resolved commits. Inspect Addressables groups/keys, scene roots, existing UI/economy/audio/feedback assets and teardown. If README examples conflict with installed source, record the drift and use verified source/tests; repair local documentation rather than copying an outdated manual-presenter example.

For each concern, record requirement → existing capability/source revision → reuse/adapter/gap → owner/asset/address → verification. Search in this order: existing project/template, imported `_Feature`, installed Dreamy package, relevant Dreamy-Game-Foundation repository. Inspect an additional package's README/dependencies/API before importing and pin its revision. Do not import duplicate sample scripts/assemblies/Resources keys or upgrade the whole foundation incidentally. User authorization to import packages persists.

Prefer editing/refactoring the existing imported sample scripts and prefabs in place when their responsibility fits. Remove superseded sample/demo code after checking consumers and serialized references; avoid keeping a copied parallel implementation. Preserve GUIDs and record local changes for future upstream merges. Use a prefab variant/configuration for a distinct skin, then a narrow game-specific adapter only for an actual game boundary. Follow repository naming/conventions, single responsibility and explicit dependencies; add abstractions only where they remove a real coupling. Write a replacement service/framework only after documenting the missing capability. A class importing a Dreamy namespace, installed packages, or a dependency list does not prove reuse. Do not justify duplicate generic UI/navigation/audio/save systems merely because the game is a clone.

## Integration invariants

- Mobile panel authoring follows `unity-ui-reskin` when available: static prefab setup, SafeArea ownership, portrait 1080x1920/landscape 1920x1080 with Match 0.5 by default unless the user specifies otherwise, Simple/preserve aspect for art and justified slicing only for stretchable frames/bars. Bind extracted fonts with persistent outline/shadow presets. Compare against original screenshots and fix the baseline preview before other responsive aspects; do not invent missing UI/functions. Preserve the template's naming/style/MVP and root-injected dependencies.
- Preserve the inspected template startup scene contract: Init/Bootstrap scene owns GameInstaller and readiness; GameInit uses the existing SceneLoader/loading screen to enter MainScene. MainScene owns game controllers/UI and consumes installed services. Keep scene GUIDs, build order and Editor Play entry consistent. Never collapse this into a single-scene bootstrap without an explicit owner request. Persistent installers must not serialize references to later-scene controllers; bind and release them at scene lifetime boundaries.
- One composition root owns ordered installation, readiness/failure, cancellation, registrations and reverse cleanup. Adapt the template's supported composition points; do not run a second installer/wallet alongside the game controller. Keep the template's default consumer working when introducing a reusable hook.
- Static catalogs/tuning use DataConfig; mutable progress/receipts/settings use Datasave or the existing wallet. Preserve old save keys/schema/codec and transaction guarantees. An adapter over an existing aggregate can be safer than a destructive currency migration. All resource holders/features observe the same authority.
- Reuse feature installer/presenter/view contracts. Use a shared presenter factory and PanelManager/UIPanel lifecycle, layers/back/cache handling; each opening owns one presenter and releases subscriptions/async/tweens. Do not create another presenter manually when the factory host already owns it.
- Author game skins as prefabs/variants using suitable original art. Reuse `_Feature` item/panel/holder/feedback prefabs when their responsibility fits. Serialized references/layout/config own presentation. Keep runtime procedural UI only for a justified dynamic role; do not make a hardcoded constructor the permanent authoring system.
- Put panel variants in Addressables with stable constants matching their actual keys; load/open through the existing Assets/UI path. Use direct prefab/atlas dependencies for item art when supported. Record instance/cache/handle lifetime and failure/retry; do not hide a missing key with a silent Resources fallback.
- Configure the existing UITweenPlayer/effect/stagger components and Feedback rig/player before writing another tween loop. Cancel/kill at the owning lifecycle boundary. Effects animate a committed outcome; they never grant currency or own gameplay authority.
- Audit scene-authored initializers as well as installer code: a retained AudioBootstrap can overwrite a game profile even when the service registration is unique. Keep one initializer, verify an actual library/key lookup and teardown/relaunch, and inspect supported bus/master-volume semantics before assuming a global master bus.
- Use the Audio profile/library/service and existing settings integration/gateways instead of parallel AudioSource pools or competing preference stores. Source clips/keys and native UI skin belong to the game; framework lifecycle belongs to the existing capability.
- Fake billing is allowed when explicitly requested and remains behind the gateway. Test success/cancel/failure/pending/restore/duplicate/relaunch/disk failure. Preserve atomic bundle delivery and acknowledge only after persistence. Fake evidence never proves real billing/store readiness.

## Maintainability and delivery gate

When migrating procedural gameplay UI, inspect whether the existing authored gameplay panel can own result/target overlays before adding more panel/adaptor classes. Keep win reward display downstream of the existing committed transaction; reopening a view must not grant again. A button callback from a previous result/offer must be cleared when that view closes. Direct world selection should resolve through the model's current blocking layer and eligibility rules, rather than duplicate them in a UI list.

Treat the return from an animated Shop as a lifecycle boundary: OnPreHide occurs before the old panel/presenter finishes teardown. Inspect the pinned panel contract before enabling a route that can immediately reopen it. Verify close/reopen/purchase/return using the same attempt and include an insufficient-wallet path.

Remove superseded paths after migration; avoid leaving two navigation/wallet/settings implementations selectable by accident. Document the install/load/open/tween/update flow and each residual exception with its reason. Preserve prefab/meta/scene references, avoid editing PackageCache, and identify local `_Feature` extensions that need a merge when samples update.

Validate compilation/Console, old saves, single ownership/teardown, panel reopen/cancellation/address failure, transaction/restore/recovery and the affected user routes. Inspect actual Game View/source comparisons and motion. Package integration, native visual parity and release readiness are separate results. Player/device/content/SDK/store gates remain deferred when the user forbids builds or postpones SDK work; do not call the clone shippable solely because Editor tests pass.

The Pixel Flow consumer exposed a real failure mode: many packages were installed while a separate bootstrap/procedural UI/audio path still bypassed their integration. This is evidence motivating the gate, not evidence that the refactor or exact clone is complete.
